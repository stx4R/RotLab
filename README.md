# RotLab — 회전 변환 실습기

오일러각·회전행렬·쿼터니언을 라이브러리 없이 직접 구현하고, 짐벌락과 보간 방식의 차이를
화면과 숫자로 동시에 보여주는 도구다. Three.js는 렌더링(씬·카메라·조명·메시)에만 쓰였고
**회전 수학은 한 줄도 라이브러리를 쓰지 않았다.** `THREE.Euler`·`THREE.Quaternion`·
`Matrix4`의 회전 생성 메서드는 프로젝트 전체에서 `src/verify.js` 안에만 등장하며,
거기서는 직접 구현을 대조할 **기준 답**으로만 쓰인다.

## 좌표 규약

- **월드는 Z-up.**
- **기체는 +x 기수, +z 위, +y 왼쪽 날개.**
- **오일러 순서는 ZYX** — yaw ψ(z축) → pitch θ(y축) → roll φ(x축).

### pitch를 +로 주면 기수가 내려간다

오른손 좌표계에서 x가 앞이고 z가 위이면 나머지 축 y는 **왼쪽으로 강제된다**
(x × y = z 를 만족해야 하므로). 이 상태에서 pitch는 y축 회전이고

```
Ry(θ)·(1, 0, 0) = (cos θ, 0, −sin θ)
```

이므로 θ > 0 이면 기수의 z성분이 음수가 된다 — 즉 **기수가 내려간다.**

항공 관례(+pitch = 기수 위)와 부호가 반대인데, 이건 구현 실수가 아니라
**오른손 좌표계와 Z-up을 동시에 요구했을 때의 수학적 귀결이다.** 항공 관례가 성립하는
NED 좌표계는 z가 아래를 향한다.

UI에서 pitch 슬라이더의 부호만 뒤집는 대안이 있었지만, 그렇게 하면 1~3단계에서 이미
측정해 둔 수치(det E, 짐벌락 실증값, 보간 통계)의 의미가 전부 바뀐다. **규약을 그대로 두고
문서화하는 쪽을 택했다.**

## 구현한 수식 — 회전

```
Rx(φ) = [[1,      0,       0     ],
         [0,  cos φ,  −sin φ     ],
         [0,  sin φ,   cos φ     ]]

Ry(θ) = [[ cos θ, 0,  sin θ],
         [ 0,     1,  0    ],
         [−sin θ, 0,  cos θ]]

Rz(ψ) = [[cos ψ, −sin ψ, 0],
         [sin ψ,  cos ψ, 0],
         [0,      0,     1]]
```

ZYX 합성:

```
R = Rz(ψ) · Ry(θ) · Rx(φ)
```

전개하면

```
R = [ cθcψ   sφsθcψ − cφsψ   cφsθcψ + sφsψ ]
    [ cθsψ   sφsθsψ + cφcψ   cφsθsψ − sφcψ ]
    [ −sθ    sφcθ            cφcθ          ]
```

역변환 `matrixToEuler`는 `asin` 대신 `atan2`를 쓴다.
`θ = atan2(−R₂₀, hypot(R₂₁, R₂₂))` — θ가 ±90° 근처일 때 `asin`은 조건수가 무너지지만
`atan2`는 그렇지 않다.

### 각속도 매핑 행렬 E

세 오일러 각속도는 각각 **그 각이 적용되는 시점의 좌표계 축**을 타고 들어온다.
그 축들을 공통 좌표계에서 열로 세운 것이 E다.

```
E = [ Rz(ψ)Ry(θ)·e₁ ,  Rz(ψ)·e₂ ,  e₃ ],        ω = E · [φ̇, θ̇, ψ̇]ᵀ

    = [ cθcψ  −sψ  0 ]
      [ cθsψ   cψ  0 ]
      [ −sθ    0   1 ]
```

**det E = cos θ 유도.** Rz는 e₃을 고정하므로 (`Rz·e₃ = e₃`, 따라서 `Rzᵀ·e₃ = e₃`)
E를 다음처럼 Rz를 밖으로 빼서 쓸 수 있다.

```
E = Rz · [ Ry·e₁ ,  e₂ ,  e₃ ]
```

det Rz = 1 이므로

```
det E = det([Ry·e₁, e₂, e₃])
      = det [[cos θ, 0, 0],
             [0,     1, 0],
             [−sin θ,0, 1]]
      = cos θ
```

## 구현한 수식 — 쿼터니언

`{w, x, y, z}` 객체. 해밀턴 곱, 켤레, 축-각 변환, 회전 적용을 직접 구현했다.

```
곱      ab = (a_w b_w − a⃗·b⃗,  a_w b⃗ + b_w a⃗ + a⃗ × b⃗)
켤레    q* = w − xi − yj − zk
축-각   q = cos(α/2) + sin(α/2)·n̂        α = 2·atan2(‖u⃗‖, w)
회전    v' = q v q* = (w² − u⃗·u⃗)v⃗ + 2(u⃗·v⃗)u⃗ + 2w(u⃗ × v⃗)
slerp   slerp(q₀,q₁,t) = ( sin((1−t)Ω)·q₀ + sin(tΩ)·q₁ ) / sin Ω,   Ω = arccos(q₀·q₁)
```

`fromMatrix`는 Shepperd 방법을 쓴다 — 네 성분 중 절댓값이 가장 큰 것을 먼저 √로 뽑는다.
w부터 뽑으면 180° 근처 회전에서 `√(1+tr) → 0` 이 되어 정밀도가 무너진다.

### 이중 덮개

**q와 −q는 같은 회전을 나타낸다.** S³ 위에서는 정반대 점이지만 SO(3)에서는 같은 원소다.
그래서 slerp의 "최단호"가 표현 선택에 좌우된다.

- `dot(q₀,q₁) < 0` 이면 q₁이 q₀의 반대쪽 반구에 있다는 뜻이고, 명세 그대로 `Ω = arccos(dot)`를
  쓰면 Ω > 90°가 되어 **회전각 180°를 넘는 먼 쪽 호**를 돈다. **q₁의 부호를 뒤집어
  짧은 쪽을 택했다.**
- `dot > 0.9995` (Ω ≈ 1.81°) 에서는 sin Ω가 0으로 가 나눗셈이 무너지므로 **nlerp
  (선형보간 후 정규화)로 대체**한다. 0.9995는 Shoemake 이래의 관례값이며 three.js·GLM·Unity가
  같은 값을 쓴다. 이 구간에서 nlerp와 참 slerp의 각도 차이는 최대 **6e-5°** 라 시각적으로도
  수치적으로도 무해하다.

두 처리 모두 없으면 아래 검증 5번이 통과하지 않는다. 부호 처리를 빼면 `dot < 0` 쌍에서
최대 오차가 **1.95** (기준 1e-9)까지 벌어진다.

## 검증 — Three.js 내장과의 대조

이 프로젝트의 검증 장치다. 직접 구현한 회전 수학에 대해 **독립적으로 구현된 기준 답이
라이브러리 형태로 존재**하므로, 그것과 성분 단위로 대조했다.

| # | 항목 | 대조 대상 | 표본 | max·오차 | 기준 |
|---|---|---|---|---|---|
| 1 | `eulerToMatrix` (ZYX) | `Matrix4.makeRotationFromEuler` | 200 | 2.220e-16 | 1e-12 |
| 2 | `quat.multiply` | `Quaternion.multiply` | 200 | 2.220e-16 | 1e-12 |
| 3 | `toMatrix`/`fromMatrix` 왕복 | 자기 무모순 | 200 | 1.110e-15 | 1e-12 |
| 4 | `quat.rotateVector` | `Vector3.applyQuaternion` | 200 | 8.882e-16 | 1e-12 |
| 5 | `quat.slerp` | `Quaternion.slerp` | 1100 | 3.331e-16 | 1e-9 |
| 6 | `gimbalMeasure` = det E | `cos θ` (해석해) | 200 | 2.220e-16 | 1e-14 |

- 5번 표본에는 **`dot(q₀,q₁) < 0` 쌍 47/100** 이 포함된다. 대척점 경우를 검사하지 못하면
  검사 자체가 무의미하므로, 그런 쌍이 하나도 없으면 실패로 처리한다.
- 6번은 θ=±90°에서 **|det E| = 6.12e-17** (< 1e-15 요구)도 함께 확인한다.
- 난수는 씨앗 고정(mulberry32)이라 실패를 재현할 수 있다.
  **씨앗 400개 전수로 실패 0건, 전 항목 최악 오차 2.442e-15.**

### 왕복 검사에서 부호를 다룬 방법

**회전행렬은 쿼터니언의 부호까지 결정하지 못한다.** `toMatrix(q) = toMatrix(−q)` 이므로
`fromMatrix`는 둘 중 하나를 골라 돌려줄 수밖에 없다. 그래서 두 방향을 모두 쟀다.

- `q → R → q'` : ±를 무시하고 `min(‖q−q'‖, ‖q+q'‖)` 로 비교
- `R → q → R'` : 부호 모호성이 없는 방향. 성분을 그대로 비교

**둘 중 큰 쪽을 그 항목의 오차로 삼았다.**

## 짐벌락

`det E = cos θ` 이므로 θ → ±90° 에서 E가 특이행렬이 되고 **자유도가 하나 사라진다.**
어떤 각속도 ω는 어떤 `(φ̇, θ̇, ψ̇)` 조합으로도 만들 수 없게 된다. 세 가지로 보인다.

### (1) 수치

| θ | 0° | 30° | 60° | 89° | 90° |
|---|---|---|---|---|---|
| det E | **1.0000** | 0.8660 | **0.5000** | 0.0175 | **0.0000** |

`|det E| < 0.05` 이면 계기판이 경고색으로 바뀐다.

### (2) 대수

θ = +90° 이면 `cos θ = 0`, `sin θ = 1` 이므로 위의 R 전개식이 이렇게 무너진다.

```
행 0 :  [0,  sφcψ − cφsψ,   cφcψ + sφsψ]  =  [0,  sin(φ−ψ),   cos(φ−ψ)]
행 1 :  [0,  sφsψ + cφcψ,   cφsψ − sφcψ]  =  [0,  cos(φ−ψ),  −sin(φ−ψ)]
행 2 :  [−1, 0,             0           ]
```

**모든 성분이 `sin(φ−ψ)`, `cos(φ−ψ)` 로만 나온다. R은 `(φ − ψ)` 하나에만 의존한다.**
θ = −90° 에서는 같은 방식으로 `(φ + ψ)` 에만 의존한다.

```
행 0 :  [0, −sin(φ+ψ),  −cos(φ+ψ)]
행 1 :  [0,  cos(φ+ψ),  −sin(φ+ψ)]
행 2 :  [1,  0,          0        ]
```

세 각 중 둘이 하나의 조합으로 뭉쳤다. 자유도 3 → 2.

### (3) 실증

위 대수의 직접적 귀결로, **θ = +90° 에서 yaw +30° 와 같은 결과를 내는 것은 roll −30° 다.**
`(φ−ψ)` 가 같아져야 하니 부호가 반대여야 한다. 그리고 **부호는 θ의 부호에 딸려 뒤집힌다.**

실측 (φ = 5°, ψ = 90°, `max|ΔR|`):

| | yaw+30 vs roll+30 | yaw+30 vs roll−30 |
|---|---|---|
| θ = +90° | 0.9962 | **1.110e-16** |
| θ = −90° | **2.220e-16** | 0.9962 |

**소멸한 자유도 방향** — θ=+90°에서 φ와 ψ를 동시에 같은 양만큼 움직이면 `(φ−ψ)`가
변하지 않으므로 자세도 변하지 않는다. δ를 5°~180°로 훑어도 `max|ΔR| = 2.22e-16`.
**아무리 움직여도 자세가 변하지 않는다.**

### 명세 정정

처음 세운 검증 기준은 *"θ=90°에서 yaw+30과 roll+30이 같아진다"* 였다.
**부호를 따져 보지 않은 서술이었고, 위 전개와 실측으로 틀렸음을 확인해 바로잡았다.**
θ=+90°에서 그 둘의 차이는 0.9962로, 일치와는 거리가 멀다. 앱의 `짐벌락 실증` 버튼은
θ 부호를 보고 짝을 자동으로 잡고, 일치·대조군·소멸 방향 셋을 모두 숫자로 찍는다.

## 오일러 보간 대 slerp

### 각속도 크기 전개

`ω = φ̇·c₁ + θ̇·c₂ + ψ̇·c₃` (c는 E의 열). 세 열은 모두 **단위벡터**다 —
회전행렬은 길이를 보존하고 e₁,e₂,e₃가 단위벡터이므로. 따라서

```
|ω|² = φ̇² + θ̇² + ψ̇² + 2φ̇θ̇(c₁·c₂) + 2φ̇ψ̇(c₁·c₃) + 2θ̇ψ̇(c₂·c₃)
```

내적을 하나씩 보면

```
c₁·c₂ = (RzRy e₁)·(Rz e₂) = (Ry e₁)·e₂ = (cos θ, 0, −sin θ)·(0,1,0) = 0
c₂·c₃ = (Rz e₂)·e₃        = (−sin ψ, cos ψ, 0)·(0,0,1)             = 0
c₁·c₃ = (RzRy e₁)·e₃      = (cθcψ, cθsψ, −sin θ)·(0,0,1)           = −sin θ
```

0이 아닌 조합은 **첫째·셋째 열의 −sin θ 하나뿐**이다. 그러므로

```
|ω|² = ψ̇² + θ̇² + φ̇² − 2·ψ̇·φ̇·sin θ(t)
```

**t에 따라 변하는 항은 `sin θ(t)` 뿐이다.** 따라서 오일러 선형보간이 등속이 되는 조건은

> **θ̇ · ψ̇ · φ̇ = 0** — 셋 중 하나라도 0이면 교차항이 t에 무관해져 등속이 된다.

θ̇ = 0 이면 sin θ가 상수라서, ψ̇ = 0 이나 φ̇ = 0 이면 교차항 자체가 사라져서다.

### 핵심 결론 — 실패 모드는 둘이고, 표준편차는 하나만 잡는다

| | 속도 요동(표준편차) | 경로 폭주(총 회전각) |
|---|---|---|
| θ̇·ψ̇·φ̇ = 0 · 극 통과 | **없음** (1e-14) | **최대 15배 이상** |
| 세 각 모두 변화 | 있음 (std/평균 19%) | 있음 |

교차항이 죽으면 오일러 lerp도 **완벽한 등속**이 된다. 그런데도 **경로는 측지선의 15배까지
늘어난다.** 표준편차만 봤다면 가장 극적인 실패를 통째로 놓쳤을 것이다.
**그래서 지표에 경로 길이와 측지선 초과율을 함께 넣었다.**

### 실측 (균일 t 격자 180스텝)

**기본 프리셋** — A(yaw 90, pitch −45, roll 5) → B(yaw 85, pitch 95, roll 10).
B의 pitch가 95°라 θ=90° 극을 실제로 가로지른다. 분해하면 A는 ψ90 θ−45 φ5,
B는 ψ−95 θ85 φ−170.

| | 평균 | 표준편차 | 최대 | 총 회전각 |
|---|---|---|---|---|
| 오일러 lerp | 1.6814° | **0.3186°** | 2.0722° | **302.647°** |
| slerp | 0.7788° | **8.37e-15°** | 0.7788° | **140.177°** (= 측지선) |

**경로 초과 +115.9% (2.16배).** 표준편차 비는 약 4e13배 — slerp는 기계 정밀도 안에서 등속이다.

**θ̇·ψ̇·φ̇ = 0 사례 (φ 고정)** — A(−70, 80, 0) → B(100, −80, 0):
오일러 평균 1.2970°, **표준편차 1.24e-14°** (slerp와 같은 수준), 총 233.451° 대 178.266°,
**초과 +31.0%**. 요동은 전혀 없는데 경로만 31% 길다.

**경로 폭주** — A(135, 85, 15) → B(145, 95, 5). θ가 양쪽 다 85°로 분해되어 θ̇ = 0:

| | 평균 | 표준편차 | 총 회전각 |
|---|---|---|---|
| 오일러 lerp | 1.8871° | 1.62e-14° | **339.676°** |
| slerp | 0.1242° | 5.70e-15° | **22.355°** |

**초과 +1419.5% — 15.19배.** slerp가 22° 도는 동안 오일러는 340° 가까이 휘돈다.
표준편차로는 두 방식이 구별되지 않는다.

## 측정 방법론

왜 이렇게 쟀는지를 적지 않으면 유리한 조건을 고른 것으로 읽힌다.

**균일 t 격자(180스텝)로 통계를 냈다.** 렌더 Δt 지터는 두 방식의 표준편차에 똑같이
섞여서 정작 재려는 차이를 가린다. 실제 렌더 프레임 통계도 함께 싣되 그 사실을 표에 명시한다.

**첫 구간과 마지막 구간을 통계에서 제외했다.** `play()` 호출 시점은 프레임 경계가 아니고
마지막은 t를 1로 자르므로 **둘 다 구조적으로 부분 프레임**이다. 제외 전 slerp 표준편차가
**0.0493°** 로 나왔는데, 180개가 0.7780°이고 딱 1개가 0.08°인 이상치 탓이었다.
제외 후 **1.06e-14°**.

**프레임별 회전각은 트레이스가 아니라 쿼터니언으로 쟀다.**

```
q_rel = q_t ⊗ conj(q_{t−1}),      α = 2·atan2(‖(x, y, z)‖, |w|)
```

트레이스 공식 `α = arccos((tr − 1)/2)` 는 `arccos`에 `1 − α²/4`를 넣는 꼴이라
α가 작을수록 무너진다 (`d/dx arccos(x)`가 x→1에서 발산한다). 참값을 축-각으로 정확히
만들어 놓고 잰 상대오차:

| 참 α | 쿼터니언 | 트레이스 |
|---|---|---|
| 179° | 0 | 5.7e-16 |
| **90°** | **0** | **4.2e-16** |
| 10° | 6.4e-16 | 1.7e-14 |
| 1° | 1.4e-14 | 3.7e-12 |
| 0.01° | 1.1e-12 | 3.5e-8 |
| 0.0001° | 1.1e-11 | 1.7e-4 |
| 0.000001° | 5.9e-9 | **1.0** (0을 반환) |

**큰 각도에서는 두 공식이 기계 정밀도로 일치한다.** 90°에서 트레이스 4.2e-16, 쿼터니언 0.

일반 재생(프레임당 ~0.7°)에서는 트레이스도 5e-12로 아직 멀쩡하다. **갈리는 건 작은 각도다.**
A≈B(0.005°) 재생에서는 프레임당 참값이 **2.778e-5°** 가 되고, 실측 최대 상대오차가
**트레이스 3.10e-3 (0.31%) 대 쿼터니언 1.01e-9** 로 갈린다. 거기서는 결정적이다.
쿼터니언 식은 `|w|`를 쓰므로 이중 덮개도 자동으로 처리된다.

## 구조 — 보정과 회전 수학의 분리

```
payload (Group)     ← 회전 수학이 계산한 R 이 그대로 들어간다
  └ fixed (Group)   ← MODEL_AXIS_FIX · 배율 · 중심이동. 상수, 한 번만 적용
       └ GLB 씬
```

```
MODEL_AXIS_FIX = [[−1, 0, 0],
                  [ 0, 0, 1],
                  [ 0, 1, 0]]
```

축 `(0,1,1)/√2` 둘레 180° 회전이고 **det = +1** 인 정상 회전이다. GLB의 로컬 축이
**기수 −X · 위 +Y · 날개 ±Z** 이므로 이를 앱 규약으로 보내는 보정이다.

```
FIX·(−1, 0, 0) = ( 1, 0, 0)   기수 → +x
FIX·( 0, 1, 0) = ( 0, 0, 1)   위   → +z
FIX·( 0, 0, 1) = ( 0, 1, 0)   날개 → ±y
```

**이 상수는 `src/model.js` 한 곳에만 있고, 회전 수학 모듈(`mat3`/`euler`/`quat`)은
이 파일을 모른다.** `model.js`가 import하는 것은 `three`, `GLTFLoader`, `scene.js`의
`setMatrix` 뿐이다.

보정이 회전 계산에 새어 들어가면 짐벌락 실측치가 달라진다. 그래서 **GLB 교체 전후로 같은
수치가 나오는지가 그 분리를 검증하는 방법이다.** 삼각대에서 GLB로 바꾼 뒤에도
`θ=+90°: 1.110e-16 / 0.9962` 는 그대로였다.

GLB 로드에 실패하면 **삼각대로 자동 폴백**하고 화면에 그 사실을 표시한다.
앱이 에셋 로딩에 묶여 멈추지 않는다.

## 한계

- **오일러각 분해는 θ=±90°에서 유일하지 않다.** `|cos θ| < 1e-6` 이면 `degenerate: true`로
  표시하고 φ=0으로 고정해 자유도를 ψ로 몬다. **값을 억지로 채우지 않는다.**
- **두 성분의 차이가 정확히 ±180°인 래핑은 방향이 원리적으로 미정이다.** 최단 방향이 둘 다
  같은 길이라 어느 쪽을 골라도 옳고, 실제로는 부동소수점 부호가 결정한다.
  이게 실제로 결과를 바꾼다: A(20, 85, −10) → B(20, 95, −10) 는 Δψ와 Δφ가 **둘 다 정확히
  ±180°** 인데, 부호 조합에 따라 오일러 경로가 **359.657° (35.97배)** 또는
  **15.703° (1.57배)** 로 갈린다. 엔진이 바뀌면 재현되지 않으므로,
  **README의 모든 프리셋은 ±180°에서 5° 이상 떨어뜨려 잡았다.**
- **모드 전환 시 자세가 최대 ~0.9° 어긋난다.** 슬라이더 단위(1°, 0.001)로 분해값을
  반올림하기 때문이다. A/B는 쿼터니언으로 따로 저장되므로 **보간 비교 결과에는 영향이 없다.**
- 재생은 `requestAnimationFrame`으로 돌지만, 창이 합성되지 않는 환경에서는 rAF가 아예
  호출되지 않는다. 100ms 안에 오지 않으면 타이머로 진행시킨다(통계는 실제 Δt를 기록).

| `src/euler.js` | ZYX 오일러 — `rotX/Y/Z`, `eulerToMatrix`, `matrixToEuler`(degenerate 분기), 각속도 행렬 E, `gimbalMeasure = det E` |
| `src/quat.js` | 쿼터니언 — 해밀턴 곱·켤레·노름·축각 변환·행렬 변환·`rotateVector`·`slerp`(최단호 + nlerp 문턱) |
| `src/verify.js` | Three.js 내장과의 대조 6항목. **프로젝트에서 THREE를 회전 기준으로 쓰는 유일한 곳** |
| `src/scene.js` | 씬·조명·짐벌 링 3개·삼각대·카메라 궤도(OrbitControls 미사용). 내 행렬을 `Matrix4.set`으로 써 넣기만 한다 |
| `src/model.js` | GLB 로딩과 `MODEL_AXIS_FIX` 축 보정, 크기 정규화, 폴백 |
| `src/compare.js` | 오일러 lerp vs slerp 재생·궤적·프레임별 회전각 측정·통계 |
| `src/main.js` | UI 배선 — 모드 토글, 계기판, 짐벌락 실증, A/B 지정과 재생 |
| `index.html` / `style.css` | 레이아웃과 importmap(`three` → `vendor/`) |
| `vendor/three.module.js` | three r185 ESM 단일 파일 번들 (커밋 대상) |
| `vendor/GLTFLoader.js` | 같은 버전의 GLTFLoader. `three`는 external로 남겨 인스턴스를 공유한다 |
| `tools/vendor.mjs` | `npm run vendor` — node_modules에서 vendor/ 재생성 |
| `tests/run.html` | 브라우저 검증 러너 (결과는 콘솔) |
| `tests/run.node.mjs` | Node 검증 러너 (`npm run verify`) |

## 프리셋 — 촬영/재현용

| | A (yaw, pitch, roll) | B (yaw, pitch, roll) | 보이는 것 |
|---|---|---|---|
| **(a) 정상** | (0, 0, 0) → yaw만 −180~180 | — | 자유도 3, `det E = 1.0000`. Z링만 자전하고 안쪽 링은 실려 돈다 |
| **(b) 짐벌락** | (90, **90**, 5) | — | `det E = 0.0000`, `degenerate: true`. yaw+30 과 **roll−30** 이 같은 회전 |
| **(c) 극 통과 보간** | (90, −45, 5) | (85, **95**, 10) | 오일러 std 0.3186° 대 slerp 8.37e-15°, 경로 초과 **+115.9%** |
| **(d) θ̇·ψ̇·φ̇=0** | (−70, 80, 0) | (100, −80, 0) | 표준편차는 둘 다 1e-14인데 경로만 **+31.0%** 길다 |
| **(e) 경로 폭주** | (135, 85, 15) | (145, **95**, 5) | 요동 없이 경로만 **15.19배**. slerp 22.4° 대 오일러 339.7° |

(b)의 `θ를 90°로` 버튼과 `짐벌락 실증` 버튼, (c)의 `짐벌락 가로지르게` 버튼이
각각 해당 상태로 바로 보낸다. 콘솔에서 재현하려면:

```js
const { poseFromEuler, measureUniform, angleFormulaCheck } = window.rotlab;
measureUniform(poseFromEuler(135, 85, 15), poseFromEuler(145, 95, 5));
angleFormulaCheck();   // 트레이스 대 쿼터니언 공식 비교표
```

## 3D 에셋 출처

`assets/plane.glb` 는 **Meshy AI**로 생성한 모델을 리메시(26,762 폴리곤)하고 텍스처를
축소(베이스컬러 1024, 금속·거칠기 512)한 것이다. **원본은 307만 폴리곤이었다.**
범위는 `[1.735, 0.658, 1.900]`, 최대축은 날개폭(로컬 Z)이며 날개폭 2.6으로 정규화해
가장 안쪽 링(반지름 1.8) 안에 들어간다 — 보정 후 실제 바운딩 구 반경 1.384.

이 모델은 **앱 안에서 실제로 회전하는 대상**이며, 렌더링 외의 계산에는 관여하지 않는다.
